# ecFlow documentation

This directory contains the ecFlow documentation, built with Sphinx and published at
https://ecflow.readthedocs.io/.

## Layout

The entry point is `index.rst`, which presents the documentation in three sections:

- **User Manual** — `overview.rst`, `install/`, `quickstart.rst`, `tutorial/`, the
  user guide under `ug/`, `glossary.rst` and `faq.rst`.
- **Reference** — the CLI reference (`client_api/`), the Python API reference
  (`python_api/`), and the REST (`rest_api.rst`) and UDP (`udp_api.rst`) APIs.
- **About** — `release_notes/`, `support.rst`, `contributing.rst`, `licence.rst`.

The reStructuredText heading markup convention used throughout is documented in the
comment at the top of `index.rst`.

## Building

The documentation is built by the `ecflow_docs` CMake target (see `CMakeLists.txt`):

```bash
cmake --build --preset <preset> --target ecflow_docs
```

This regenerates the reference pages described below and then runs a single Sphinx
pass over this directory. The Python packages needed by the Sphinx build are listed
in `requirements.txt` (also used by readthedocs.io, see `.readthedocs.yml` at the
repository root).

## Generated reference pages are committed on purpose

Parts of the reference documentation are **generated files committed as if they were
sources**. This is a deliberate design decision, not an oversight: readthedocs.io
builds the documentation in an environment where no C++ build environment is
available at all, so nothing derived from the compiled ecFlow artefacts can be
produced there. Committing the generated pages keeps the full documentation buildable
from a plain source checkout with nothing but Sphinx.

Two areas follow this approach:

- **CLI reference** (`client_api/api/*.rst` and `client_api/index.rst`), generated by
  `client_api/build.py`: the freshly built `ecflow_client --help=<entry>` is run for
  each command and option, and its output is combined with the hand-written
  description files under `client_api/desc/`.
- **Python API reference** (`python_api/reference/*.rst` and
  `python_api/python_api.rst`), generated by `python_api/extract_api.py`: the freshly
  built `ecflow` Python module (located via `PYTHONPATH`) is introspected and one
  page is written per public class, from the docstrings compiled into the module;
  `python_api/python_api.py` then writes the categorised index, driven by
  `python_api/categories.yaml`.

Two consequences follow:

- A change to a CLI help text or a Python docstring in the C++ sources is not visible
  in the documentation until the pages are regenerated (by building the
  `ecflow_docs` target) **and the resulting diffs are committed**. Such diffs mirror
  the source changes and are the natural place to review them.
- Never edit the generated files by hand — the next regeneration overwrites them.
  Fix the help texts, docstrings, description files or generation scripts instead.

## Adding new API elements

- A new `ecflow_client` command or option is picked up automatically from
  `--help=summary` / `--help=option`; an optional long description can be added under
  `client_api/desc/<name>.description`.
- A new public class in the `ecflow` Python module is picked up automatically by
  `extract_api.py`, but its page is only reachable once the class name is added to
  the appropriate category in `python_api/categories.yaml`. Module-level functions
  are currently not extracted.
